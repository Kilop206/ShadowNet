# Milestone 4 — Reliability

Versão 0.4.0. O fluxo HTTPS → Gateway → WSS/mTLS → Agent → serviço local do
M3 permanece no protocolo v3. O M4 aplica admissão por orçamento de buffers,
backpressure, prioridade de controle e prazo de escrita; valida recuperação
durante tráfego concorrente e recebedores lentos.

## Arquivos e decisões

| Área | Arquivos criados/alterados |
|---|---|
| Reservas RAII | `libs/core/include/shadow/core/buffer_budget.hpp` |
| Fila limitada/prioridade | `libs/protocol/include/shadow/protocol/outbox.hpp` |
| Controle de I/O | `libs/networking/src/secure_session.hpp/.cpp`, `secure_transport.cpp` |
| Admissão HTTP | `libs/networking/src/https_server.cpp`, `local_http.hpp/.cpp` |
| Respostas adiadas/CANCEL | `libs/networking/src/proxy_router.hpp/.cpp` |
| YAML/defaults | `libs/configuration/include/shadow/configuration/config.hpp`, `libs/configuration/src/config.cpp`, `config/*.wss.yaml` |
| Testes | `tests/unit/reliability.cpp`, `tests/e2e/reliability.py`, harness/peers/backend HTTP, `tests/CMakeLists.txt`, regressão de versão CLI |
| Build/CI/docs | `CMakeLists.txt`, `.github/workflows/ci.yml`, README e documentação de arquitetura/configuração/ameaças/testes/deploy/limitações/troubleshooting/roadmap |

- A reserva só retorna após o último handler/proprietário liberar seus buffers.
  O orçamento local do Agent sobrevive a reconexões, evitando sobreposição de
  reservas antigas e novas durante cancelamento.
- HTTP público aguarda reserva FIFO após validar headers e antes de ler corpo
  ou enviar 100-continue. A espera respeita o deadline original e não acumula
  corpos. TLS/headers/estruturas fixas também têm limites por conexão.
- O Agent guarda respostas prontas dentro de slots/orçamento e tenta enviá-las
  quando a fila drena. Saturação normal deixa de encerrar o túnel. CANCEL remove
  respostas ainda adiadas, sem desfazer efeitos do serviço.
- Há oito posições reservadas para controle, uma escrita ativa imutável e
  limite de bytes/mensagens incluindo essa escrita. CANCEL mantém FIFO com
  REQUEST; não pode ultrapassar a requisição que cancela.
- Escrita WSS tem deadline independente; buffer de fragmentação passou de 512 B
  a 16 KiB. Rejeição por fila cheia acontece antes da serialização do envelope.
- Não há nova dependência, streaming ou alteração de framing/versão na rede.

Fórmulas, defaults e custos excluídos: [controle de recursos](../architecture/reliability.md).
As reservas são admissão conservadora de buffers, não medição ou teto de RSS.

## Build e verificação executada

Windows x64, MinGW-w64/GCC 16.2.0, CMake 4.4.3, OpenSSL 4.0.3 e LLVM 23.1.3.

```powershell
cmake --preset bootstrap -G 'MinGW Makefiles' -B build/mingw -DOPENSSL_ROOT_DIR=C:/openssl-4.0.3/x64
cmake --build build/mingw --parallel 3
ctest --test-dir build/mingw -V
./scripts/check-static.ps1 -BuildDir build/mingw
cmake --install build/mingw --prefix build/install
./build/install/bin/shadow.exe version
```

- **5/5 suítes CTest aprovadas**; **432 assertions em 16 casos Catch2**.
- M1: 10 cenários aprovados e um SIGTERM POSIX ignorado no Windows.
- M2/v3: 21 cenários aprovados e um SIGTERM POSIX ignorado no Windows.
- M3: **26 cenários HTTP E2E aprovados**, incluindo concorrência e isolamento.
- M4: **9 cenários aprovados**, sem skips: FIFO/100-continue, upload abandonado,
  leitor HTTPS lento, orçamento do Agent, limite global WSS antes de TLS,
  validação YAML, resposta adiada/CANCEL/retomada, timeout de escrita e carga.
- clang-tidy: 17 unidades de produção analisadas; corrigidas as advertências
  novas de largura de inteiros e acesso à resposta opcional. A unidade alterada
  foi reanalisada sem diagnóstico do projeto. Avisos de dependências são filtrados.

## Carga sustentada local executada

```powershell
$env:SHADOW_LOAD_SECONDS='30'
$env:SHADOW_LOAD_WORKERS='16'
ctest --test-dir build/mingw -R e2e.reliability -V
Remove-Item Env:SHADOW_LOAD_SECONDS, Env:SHADOW_LOAD_WORKERS
```

Ensaio nativo de **30,025 s**, **16 workers**, POSTs binários nos dois serviços,
com **duas mortes/reinícios do Gateway** durante a carga:

| Medida observada | Resultado |
|---|---:|
| Requisições concluídas com resposta correta | 14321 |
| Falhas transitórias atravessando janelas de interrupção | 28 |
| Erros inesperados / respostas corrompidas ou trocadas | 0 |
| Requisições vistas nas origens | 14336 |
| IDs de POST repetidos na origem | 0 |
| Latência p50 / p95 das respostas concluídas | 30,877 / 49,446 ms |

Houve mais POSTs recebidos na origem que respostas concluídas porque a morte
do Gateway pode perder a resposta de uma operação já executada. Nenhum POST
foi repetido automaticamente. Isso não garante execução exactly-once de uma
aplicação; o cliente precisa de idempotência quando sua operação exigir.

O ensaio inicial de 30 s identificou um prazo fixo de join no harness, corrigido
para acompanhar a duração escolhida. Os números acima são da execução que
terminou aprovada após a correção. Não houve relaxamento de validação de TLS,
integridade, correlação ou detecção de replay para aprovar carga.

O JSON local fica em `build/mingw/tests/reliability-load.json` e é sobrescrito
em cada ensaio aprovado; a execução de 30 s foi preservada localmente em
`build/mingw/m4-load-30.json`. O CI executa 5 s/12 workers e exporta seu próprio
relatório por job. Essas medições descrevem apenas o host de teste, sem
benchmark de produção, medição de RSS ou promessa de throughput de WAN.

## Laboratório Linux/Docker

```powershell
python scripts/dev-certificates.py --output build/dev-pki-m4
$env:SHADOW_PKI_DIR='../build/dev-pki-m4'
docker compose -p shadownet-m4 -f docker/compose.yaml up --build -d
python scripts/check-demo.py --ca-file build/dev-pki-m4/ca.crt
docker compose -p shadownet-m4 -f docker/compose.yaml restart gateway
python scripts/check-demo.py --ca-file build/dev-pki-m4/ca.crt
docker compose -p shadownet-m4 -f docker/compose.yaml down
```

O gerador recusa sobrescrever uma PKI. Usar pasta nova; a CA descartável não
deve ser instalada no trust store nem reutilizada em produção. A imagem M4
foi compilada no Linux e o primeiro lote de 16 requisições HTTPS, concorrência
8 e dois serviços, passou com SAN/SNI e CA verificados.
Na imagem final, mais 16 pedidos passaram antes e outros 16 depois de
reiniciar o Gateway. O Agent reconectou e registrou ambos os serviços. Os
quatro contêineres encerraram com código 0; contêineres e rede do laboratório
foram removidos. Instalação local, versão `ShadowNet 0.4.0` e validação offline
de ambas as configurações também passaram.

## Limitações e próximo milestone

Os corpos continuam completos e limitados a 1 MiB. Reservas fixas são
conservadoras para mensagens pequenas. Não há streaming/SSE, HTTP/2, upgrade
WebSocket de aplicações, failover, balanceamento nem política por tenant.
Clientes/TLS/kernel/allocators e logs têm overhead fora do orçamento de
buffers; limites operacionais do SO continuam necessários. Heartbeat pode
expirar se uma mensagem ativa ficar bloqueada por tempo excessivo.

CANCEL é best effort e não desfaz efeitos locais. A origem não recebe conexões
da internet pelo ShadowNet, mas aplicações/conteúdo/DNS podem revelar seu IP.
Não há invisibilidade para LAN, ISP ou administradores. Não foi validado
NAT/CGNAT físico ou carga de produção distribuída.

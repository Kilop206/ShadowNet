# Milestone 2 — Secure Tunnel

Entrega: túnel WSS persistente, TLS 1.3 com mTLS, autorização por fingerprint,
handshake versionado, heartbeat correlacionado, reconexão com backoff/jitter
e fechamento controlado. O diagnóstico local do M1 permanece funcional.
**Proxy HTTP, registro/publicação de serviços e roteamento são M3.**

## Arquivos e decisões

- `libs/security/`: `credentials.hpp`, `tls.hpp`, `tls.cpp`, validadores de
  fingerprint; OpenSSL 3.0+, X.509 estrito, EKU/validade/chave local, SAN DNS/IP,
  mTLS obrigatório, sem retomada TLS e sem 0-RTT.
- `libs/protocol/`: `tunnel.hpp`/`tunnel.cpp`, envelope binário v2 e payloads
  HELLO, WELCOME, PING, PONG e GOODBYE, até 268 B.
- `libs/networking/`: `secure_transport.hpp`, `secure_session.hpp/.cpp`,
  `secure_transport.cpp`; sessão Beast/SSL separada de controle de agentes,
  identidades ativas, deadlines, fila de quatro mensagens e reconexão.
- `libs/configuration/`: schema WSS, arquivos TLS relativos ao YAML,
  autorização, permissões Unix, reconexão e heartbeat; sem opções inseguras.
- `apps/common/commands.cpp`: despacho por transporte e validação TLS offline;
  sem comandos fictícios de status/stop.
- `CMakeLists.txt`, `libs/CMakeLists.txt`, `cmake/Dependencies.cmake`:
  versão 0.2.0, Beast e OpenSSL, Winsock compartilhado e ajuste MinGW Debug
  `-O1 -g1 -Wa,-mbig-obj` para a unidade de templates SSL/WebSocket.
- `config/agent.wss.yaml`, `config/gateway.wss.yaml`: templates sem segredos;
  `scripts/dev-certificates.py`: CA efêmera e configurações funcionais, sem
  alterar trust stores e sem sobrescrever credenciais existentes.
- `tests/unit/tunnel.cpp`, `tests/integration/secure_transport.py`,
  `tests/CMakeLists.txt`, `tests/integration/local_transport.py` e
  `tests/e2e/README.md`: cobertura nova e preservação da suíte M1.
- `.github/workflows/ci.yml`: OpenSSL nos jobs GCC/Clang/sanitizers/MinGW.
- `docker/Dockerfile`, `docker/compose.yaml`, `docker/entrypoint.sh`: WSS entre
  namespaces separados; chave leaf em tmpfs, CA privada nunca montada, porta
  do laboratório publicada somente em loopback do host.
- `.gitattributes`: texto normalizado em LF para scripts/contêineres portáteis.
- `README.md`, `THIRD_PARTY_NOTICES.md`, `examples/basic-tunnel/README.md` e
  documentação de arquitetura, configuração, protocolos, segurança, instalação,
  VPS, testes, troubleshooting, limitações e roadmap atualizados.

Autorização usa SHA-256 do certificado leaf DER, não CN nem nome autodeclarado.
Uma identidade já ativa não pode ser substituída por uma conexão concorrente.
O Agent verifica o hostname certificado e inicia todas as conexões; não abre
listener nem altera firewall/roteador. Proteção da origem não equivale a
invisibilidade na LAN, para o ISP ou para o operador do Gateway.

## Build e demonstração

Ambiente local: Windows x64, GCC/MinGW-w64 16.2.0, CMake 4.4.3,
Python 3.14.3, OpenSSL 4.0.3 (API compatível 3.0+) e LLVM 23.1.3.

```powershell
cmake --preset bootstrap -G 'MinGW Makefiles' -B build/mingw -DOPENSSL_ROOT_DIR=C:/openssl-4.0.3/x64
cmake --build build/mingw --parallel 3
ctest --test-dir build/mingw -V
./scripts/check-static.ps1 -BuildDir build/mingw
python scripts/dev-certificates.py
./build/mingw/bin/shadow-gateway.exe --config build/dev-pki/gateway.wss.yaml
# Outro terminal:
./build/mingw/bin/shadow-agent.exe --config build/dev-pki/agent.wss.yaml
```

No layout local também foram informados `OPENSSL_INCLUDE_DIR`,
`OPENSSL_SSL_LIBRARY` e `OPENSSL_CRYPTO_LIBRARY` explicitamente. MSVC não é
necessário para compilar ShadowNet. Pacotes binários e instalação de serviço
continuam no roadmap M7.

## Resultados executados

- Build dos três executáveis e testes: aprovado no MinGW-w64.
- CTest: **3/3 suítes aprovadas**.
- Catch2: **164 assertions em 10 casos**, aprovadas.
- Integração M1: **10 cenários aprovados, 1 ignorado** (SIGTERM no Windows).
- Integração M2: **21 cenários aprovados, 1 ignorado** (SIGTERM no Windows).
- O M2 cobre mTLS válido/negado, certificados ausentes/estrangeiros/expirados,
  EKU, hostname/CA, fingerprint não autorizado, HELLO divergente, duplicação,
  duas identidades, TLS inferior, upgrade/frames inválidos, replay/ausência de
  heartbeat, deadlines, limite de conexões, backoff/jitter e recuperação.
- Fechamento WebSocket e TLS `close_notify` validado por peer independente
  também no Windows, além da verificação de sinais POSIX reservada ao CI Linux.
- clang-tidy LLVM 23.1.3: treze unidades de produção analisadas sem diagnósticos
  no código do projeto. Headers externos são filtrados; a operação de bits
  positivos exigida pela API OpenSSL/Asio tem uma supressão pontual documentada.
- Instalação local, versão 0.2.0 e validação offline de configuração WSS aprovadas.
- Imagem Docker Linux construída; Gateway, Agent e API iniciados. Heartbeat
  WSS/mTLS entre namespaces separados e fechamento/reconexão após reinício do
  Gateway verificados. A API respondeu diretamente no namespace do Agent;
  isso não é evidência de encaminhamento HTTP pelo túnel.
- CI remoto só é considerado aprovado após sua execução; resultados pendentes
  não são presumidos como sucesso.

Os testes identificaram e orientaram correções reais: certificados efêmeros
sem AKI exigido pelo Python 3.14, vínculo Winsock para consumidores do Asio,
segunda chamada desnecessária a TLS shutdown (Beast já faz o teardown) e
conflito de usuário/grupo `shadow` na imagem Ubuntu.

## Limitações e próximo passo

Sem HTTP ou E2E de publicação, autorização de domínios, CRL/OCSP, hot reload,
rotação automática, auditoria externa ou inspeção de ACL Windows. Certificados
são validados no handshake; conexões existentes não são revalidadas a cada
heartbeat. A política é removida por alteração de configuração e reinício.
O laboratório não comprova redes NAT/CGNAT físicas nem desempenho de produção.

# Milestone 3 — Reverse Proxy MVP

Versão 0.3.0. Implementado o caminho Cliente HTTPS → Gateway → WSS/TLS 1.3/mTLS
→ Agent → serviço HTTP local → cliente. Dois serviços distintos são publicados
por hostname, com registro autorizado, IDs e isolamento de respostas concorrentes.
O Agent continua iniciando toda conexão ao Gateway, sem abrir listener na origem.

- HTTPS de visitantes usa contexto de servidor separado e não exige certificado
  cliente; a porta WSS mantém mTLS e validação X.509 estrita.
- A política vincula pares serviço/hostname à identidade do certificado. O
  Gateway publica apenas registros autorizados, atomicamente, sem destinos
  internos no protocolo. O Agent confere serviço/Host e usa IP/porta de loopback.
- Protocolos anteriores não são aceitos no túnel v3; ambos os binários precisam
  ser atualizados. O diagnóstico TCP local v1 continua separado.
- Mensagens HTTP completas têm teto de 1 MiB de corpo, 16 KiB de headers e IDs
  não reutilizados. Pendências guardam a sessão responsável, têm prazo e CANCEL.
  Respostas de outro agente são rejeitadas; respostas antigas são descartadas.
- Métodos, query/target, status, headers end-to-end repetidos e corpos binários
  são preservados. Há HEAD, chunked/EOF, 100-continue e OPTIONS/Max-Forwards.
  Framing ambíguo é rejeitado; campos hop-by-hop são removidos e enquadramento
  reconstruído. Metadados de proxy do visitante não são confiados.
- Tetos de conexão, requisições em voo, fila/bytes, deadlines e token bucket
  global limitam recursos. O M4 refinará orçamento global/backpressure.

## Build e testes executados localmente

Windows x64, GCC/MinGW-w64 16.2.0, CMake 4.4.3, OpenSSL 4.0.3 e LLVM 23.1.3.
O runtime também foi construído no Docker Linux com OpenSSL 3 e GCC da imagem.

```powershell
cmake --preset bootstrap -G 'MinGW Makefiles' -B build/mingw -DOPENSSL_ROOT_DIR=C:/openssl-4.0.3/x64
cmake --build build/mingw --parallel 3
ctest --test-dir build/mingw -V
./scripts/check-static.ps1 -BuildDir build/mingw
cmake --install build/mingw --prefix build/install
./build/install/bin/shadow.exe version
./build/install/bin/shadow.exe config validate --type gateway --config build/dev-pki-m3/gateway.wss.yaml
```

Resultados:

- **4/4 suítes CTest aprovadas**.
- **335 assertions em 14 casos Catch2**, aprovadas.
- Regressão M1: 10 cenários aprovados, 1 ignorado por ser SIGTERM POSIX.
- Regressão de segurança do M2 em v3: 21 cenários aprovados, 1 ignorado por
  SIGTERM POSIX. Certificados inválidos/expirados, EKU/hostname/pin e heartbeat
  continuam sendo testados.
- **26 cenários E2E HTTP aprovados**, sem skips no Windows: dois serviços,
  16 pedidos simultâneos, métodos, headers, status, HEAD, corpos binários/gzip,
  chunked/EOF, 100-continue, limites, CANCEL, falhas e recuperação.
- Peers independentes verificaram registro atômico, proibição de destino
  arbitrário, resposta forjada por outro agente e resposta atrasada não
  satisfazendo uma requisição nova.
- clang-tidy: **17 unidades de produção analisadas sem diagnósticos no código
  do projeto**. Avisos de dependências são filtrados, sem alegar auditoria delas.
- Instalação local, versão `ShadowNet 0.3.0` e validação offline de ambas as
  configurações, incluindo o contexto HTTPS público, aprovadas.
- Primeiro laboratório Docker: **16 requisições HTTPS verificadas nos dois
  serviços**, concorrência 8, com SAN/SNI e CA validados pelo cliente.
- Imagem revisada e recuperação: o verificador aprovou novamente os dois
  hostnames antes e depois de reiniciar o Gateway. O Agent reconectou com nova
  sessão e registrou os dois serviços outra vez. Chave em tmpfs: modo **0600**,
  UID 1000. **Gateway, Agent, API e website encerraram com código 0**; seus
  contêineres e rede de laboratório foram removidos ao final.

O teste de conexão recusada foi tornado determinístico usando um peer que
aceita e fecha a conexão. A demora do sistema operacional ao reportar uma
porta fechada pode legitimamente resultar em 504, em vez de 502, se o prazo
expirar primeiro; a implementação não mascara esse comportamento.
Casos adicionais reproduziram transferência `gzip, chunked` sem decodificação
do transfer coding. O proxy passou a rejeitar codings não suportados nos dois
sentidos; `Content-Encoding: gzip` permanece transparente e tem teste positivo.
Uma regressão reproduziu erros HEAD que encerravam a sessão inteira. Respostas
de erro agora preservam o comprimento da representação sem enviar corpo, e o
teste verifica que outros serviços e requisições pendentes permanecem ativos.

## Demonstração reproduzível

```powershell
python scripts/dev-certificates.py --output build/dev-pki-m3
$env:SHADOW_PKI_DIR='../build/dev-pki-m3'
docker compose -p shadownet-m3 -f docker/compose.yaml up --build -d
python scripts/check-demo.py --ca-file build/dev-pki-m3/ca.crt
docker compose -p shadownet-m3 -f docker/compose.yaml restart gateway
python scripts/check-demo.py --ca-file build/dev-pki-m3/ca.crt
docker compose -p shadownet-m3 -f docker/compose.yaml down
```

O gerador recusa sobrescrever uma PKI existente. Usar outra pasta/variável para
uma geração nova. No Linux, exportar `SHADOW_PKI_DIR` e configurar UID/GID dos
arquivos conforme o guia. Não instalar a CA descartável no sistema ou em produção.
O verificador faz GETs de readiness por até 10 s para aguardar recadastro após
reinício; erros TLS/identidade falham imediatamente, e o lote verificado não
é repetido. Isso não altera a regra de ausência de replay no proxy.

## Limitações e próximo passo

O MVP não faz streaming/SSE, HTTP/2, upgrade WebSocket de aplicações, CONNECT,
TRACE ou keep-alive público; usa um request/response por conexão. Headers
recebidos têm limite de 64 campos, target 8192 B e corpo 1 MiB. Não há benchmark
de produção, validação física de NAT/CGNAT, failover ou balanceamento.

CANCEL fecha I/O, mas não desfaz efeitos da aplicação; POST não é repetido após
reconectar. Conteúdo/redirects/headers próprios da aplicação ainda podem revelar
endereços. Proteger o IP da origem dos visitantes não implica invisibilidade na
LAN, para o ISP ou para operadores do Gateway.

CRL/OCSP, hot reload, rotação de certificados e inspeção de ACL Windows seguem
no M5. O Gateway continua precisando de operação e atualização administradas.
